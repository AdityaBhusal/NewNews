# ADR-0007: Deploy-first ordering; hardening slimmed (defer LISTEN/NOTIFY + latency harness)

**Status:** Accepted — 2026-10-16

## Context

M3 ("hardening") originally contained four items: operator hardening of retries/dead-letter,
upgrading SSE cross-process notify from 200 ms DB polling to Postgres `LISTEN/NOTIFY`, a
latency measurement harness reporting p50/p95/p99, and logging dashboards. Two facts argued
against doing all of it now:

1. **Measured latency is already 10× under budget** — eligible → SSE receipt measured
   117 ms against a < 2 s objective. Replacing polling with `LISTEN/NOTIFY` would buy no
   user-visible improvement at the current scale (a single demo client), while adding a
   new failure mode (notify delivery vs. poll correctness).
2. **Percentiles need volume to mean anything.** With demo-sized traffic (~tens of items),
   a "p95" is statistical noise, and building infrastructure to compute it is effort spent
   on a number nobody can act on.

Meanwhile the system's *outer* end-to-end path (cloud deployment: remote Postgres,
migrations on deploy, worker as a separate hosted process, SSE from a public URL) was
entirely unproven — a bigger credibility gap than any internal polish.

## Decision

1. **Order the milestones deploy-first:** finish M4 (Render: env, migrations, worker,
   remote E2E) before M3.
2. **Slim M3** to what earns its keep now:
   - dead-job visibility (surface `status='dead'` jobs to an operator — the genuinely
     missing hardening piece);
   - latency as a **one-shot SQL query** over columns already stamped
     (`eligible_at`, `delivered_at`) returning count + p50/p95 — no harness.
3. **Defer** `LISTEN/NOTIFY`, the percentile load harness, and dashboards, with an explicit
   revisit trigger: concurrent SSE clients growing beyond a handful, or p95 approaching the
   budget, or production-grade alerting being required.

## Consequences

- No push-notify or percentile infrastructure to operate until load justifies it;
  `docs/roadmap.md` marks the deferred items and their triggers rather than deleting them.
- M3 shrinks to a half-day-scale checklist; M4 unblocks the demo story
  ("works end-to-end in the cloud, publicly").
- The 200 ms poll remains the notify mechanism; architecture docs continue to describe it
  as the M1→M3 baseline with `LISTEN/NOTIFY` as the named upgrade path.
