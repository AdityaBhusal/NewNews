# ADR-0002: PostgreSQL over SQLite

**Status:** Accepted

## Context

The system runs at least two processes against one database (API and worker), plus concurrent
client requests. It needs JSON columns (topics, locations, audit detail, payloads), a
concurrency-safe job queue (ADR-0003), and — planned for M3 — `LISTEN/NOTIFY` for cross-process
notification. A **remote Postgres instance is already available to the team**, and the target
deployment platform (Render) offers managed Postgres via a `DATABASE_URL` connection string.

## Decision

Use **PostgreSQL 17** as the single datastore: a `postgres:17-alpine` Compose service locally,
`DATABASE_URL` (`postgresql+psycopg://…`) pointing at remote/Render Postgres in deployment.
SQLAlchemy 2.0 async with the `psycopg` driver; `JSONB` for structured columns.

## Alternatives considered

- **SQLite** — viable zero-install option and attractive for tests. Rejected on the
  **single-writer** limit (SQLite FAQ #5): an API process writing ingestion data while a worker
  process claims jobs and a delivery path commits would serialize and contend on the single
  write lock. Also lacks `LISTEN/NOTIFY`, and moving to a client/server DB later would mean a
  migration mid-project.
- **Other client/server DBs (MySQL)** — no advantage here; Postgres is what the team already runs
  and what the deploy target supports first-class.

## Consequences

- Concurrency is a non-issue: `FOR UPDATE SKIP LOCKED` (ADR-0003) and the ingestion unique
  constraint both rely on Postgres semantics.
- `JSONB` columns and GIN-indexing options are available without extra infra.
- `LISTEN/NOTIFY` upgrade path for M3 requires no new dependency.
- A database server is now a prerequisite for local dev and tests — accepted: Compose provides
  `db`, and integration tests skip unless `TEST_DATABASE_URL` points at a disposable database
  (unit tests stay offline).
- Local and remote configuration differ only by the `DATABASE_URL` env var.
