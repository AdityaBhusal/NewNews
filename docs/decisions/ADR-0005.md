# ADR-0005: Modular monolith — one image, two processes (api/worker); Compose locally, Render to deploy

**Status:** Accepted

## Context

The pipeline has clear stages (ingest, extract, validate, enrich, match, deliver) and two runtime
shapes: a request-serving API and a long-running background worker. The team is small, the scale
is prototype-level, and the deliverable is a technical assessment where **clear module
boundaries and operational simplicity** are the point. Deployment target is Render, which
explicitly recommends Docker images when OS-level packages are needed. The host must not require
any tooling installs beyond Docker: **ffmpeg and Tesseract (`eng` + `nep`) must live inside the
container**, and the same code must run locally (Compose) and in deployment.

## Decision

- **Modular monolith**: one repository and one Python codebase; stages separated by module
  boundaries (`app/pipeline/*`), not network calls.
- **Single container image** (`python:3.13-slim` + `apt` ffmpeg, tesseract-ocr, tesseract-ocr-eng,
  tesseract-ocr-nep) used by three commands: `uvicorn app.api.main:app` (api),
  `python -m app.worker` (worker), `alembic upgrade head` (migrate).
- **Two long-running processes** (`api`, `worker`) + `db`, orchestrated by **Docker Compose**
  with healthchecks, a volume, and `.env` config; the same image deploys on **Render** as a Web
  Service (api) + Background Worker (worker) with different start commands.

## Alternatives considered

- **Microservices per stage** — independent scaling and isolation, but adds network boundaries,
  serialization, distributed tracing, and deploy surface for a single-team prototype; nothing in
  M1 needs a network boundary between stages.
- **Separate images for api and worker** — no benefit (identical contents, different CMD) and a
  risk of drift between builds; one image keeps local and deployed artifacts identical.
- **Host-level ffmpeg/Tesseract installs** — simpler image, but contradicts the requirement that
  no developer or host performs OS-level installs (README — System choices) and complicates Render deploys.

## Consequences

- `docker compose up --build` is the single local entry point; no host packages beyond Docker.
- Shared types, models, and settings between api and worker — no serialization or version skew
  between services.
- Scaling is coarse: api and worker scale independently (different services) but share one image
  build; horizontal worker scaling is already safe thanks to `SKIP LOCKED`.
- Boundaries are enforced by convention and the import graph, not by the compiler or a deploy
  unit — disciplines like "pipeline modules never import `app.api`" must be reviewed in code
  review.
- The image is larger than a pure-Python one because of ffmpeg/Tesseract — accepted (Layer
  caching keeps rebuilds cheap).
- Render free tier has ephemeral disks: media files under `/data/media` do not persist —
  documented limitation, S3-compatible storage deferred (M4).
