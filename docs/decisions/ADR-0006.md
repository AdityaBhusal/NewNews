# ADR-0006: REST + SSE for delivery (DB polling in M1, LISTEN/NOTIFY in M3) over WebSockets / mobile push

**Status:** Accepted

## Context

Matched items must reach subscribed clients fast (**< 2 s p95 from `eligible` to receipt**) and
durably: a client that reconnects must recover what it missed. The news direction is one-way
(server → client). The `api` and `worker` are separate processes (ADR-0005), so the process
that marks an item `eligible` (worker) is *not* the process holding the client connection
(api) — cross-process notification is required. Delivery state must survive restarts of either
side.

## Decision

- **REST + Server-Sent Events** as the delivery pair:
  - `GET /api/v1/events` — SSE stream (`text/event-stream`), one event per matched item with
    `id:` = the `deliveries.id` bigint, `event: news`, JSON payload; `: keepalive` heartbeat
    every 15 s.
  - `GET /api/v1/news` — pull-based retrieval with a `since_id` cursor and explicit
    `ack=true` receipt confirmation; also the recovery path for anything missed while offline.
- **Durable resume**: the `deliveries` table (unique per item+client, `pending → sent`) is the
  source of truth; the browser's built-in `Last-Event-ID` header (or `last_event_id` query
  param) becomes the stream cursor, giving idempotent resume without extra state.
- **M1 cross-process notify = DB polling** every 200 ms (`SSE_POLL_INTERVAL_MS`); the worker's
  job claim loop also polls at 200 ms.
- **M3 upgrade**: Postgres `LISTEN/NOTIFY` to wake the SSE handler immediately, keeping polling
  as a fallback so no event can be lost (see ADR-0003 consequences).

## Alternatives considered

- **WebSockets** — bidirectional capability that a one-way news feed does not need; adds proxy,
  keepalive, and reconnect complexity that SSE gets for free via `EventSource` and the standard
  `Last-Event-ID` reconnect behaviour. Rejected as more capability than required.
- **Mobile push (FCM/APNs)** — reaches devices without a held connection, but requires platform
  credentials, app distribution, and tokens; deferred as future work (M5 decides the mobile
  shape), not required for server-side clients.
- **Long-polling REST only** — simpler transport but a new request per wait, no server push, and
  worse latency characteristics than a held stream.
- **In-process pub/sub** — impossible across the api/worker process split and lost on restart.
- **`LISTEN/NOTIFY` from day one** — better latency immediately, but requires a dedicated
  listener connection per stream plus reconnect/missed-notification handling; deferred to M3 to
  keep M1 minimal. Polling makes the correctness argument trivial: the table is always re-read.

## Consequences

- No new infrastructure or protocols: delivery runs over plain HTTP, works behind standard
  proxies (`X-Accel-Buffering: no` set to defeat buffering), and uses browser-native reconnect.
- Durability and idempotency come from the `deliveries` table: exactly one row per
  (item, client), never double-sent to a connected client, and REST `since_id` covers missed
  events.
- Up to **200 ms added notification latency** per event — well inside the 2 s budget, and the
  reason the metric (`eligible_at` → receipt) is logged as `latency_ms` per delivery.
- Each open SSE stream issues a small DB query every 200 ms; connection count drives DB load
  until M3's `LISTEN/NOTIFY` lands.
- SSE is one-way; any future client → server channel (e.g. review acknowledgements) needs a
  separate REST or WebSocket mechanism.
