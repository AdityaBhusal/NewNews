# ADR-0003: Postgres-backed job queue over Redis/Celery/RabbitMQ/Hangfire

**Status:** Accepted

## Context

Pipeline stages (`extract → validate → enrich → match`) must run asynchronously after
ingestion, with **retries, backoff, and dead-letter semantics**, safe against multiple worker
processes. The project is a prototype at modest scale where operational simplicity and
"demonstrable engineering" matter more than peak throughput. Postgres is already required for
everything else (ADR-0002).

## Decision

Use a **`pipeline_jobs` table as the queue**:

- Claim with a single statement using `FOR UPDATE SKIP LOCKED` (skip already-claimed rows
  instead of blocking), setting `status='running'`, `locked_by`, `locked_at`, `attempts+1`.
- Schedule via `run_at`; retry with exponential backoff `5 s · 2^(attempts−1)`
  (`JOB_RETRY_BASE_SECONDS`), and **dead-letter** (`status='dead'` + item `failed`) after
  `JOB_MAX_ATTEMPTS = 3` attempts.
- Worker idles with a 200 ms poll (`WORKER_POLL_INTERVAL_MS`); a stage's next stage is
  enqueued in the same transaction that marks the current job `succeeded`.

## Alternatives considered

- **Redis + Celery** — mature, but adds a broker (and usually a result backend) to operate,
  monitor, and back up; extra infrastructure not justified at prototype scale. Retries and
  dead-lettering would be configured in Celery rather than "for free" in the datastore.
- **RabbitMQ** — full-featured broker, but another service to run, monitor, and secure; AMQP
  semantics are more than one-way stage execution needs.
- **Hangfire** — attractive retry/dashboard story, but it is the .NET ecosystem (not our runtime,
  ADR-0001) and its **official storages are SQL Server / Redis only**, so it would not use our
  Postgres either.

## Consequences

- No new infrastructure, no new credentials: `docker compose up` still starts only `db`,
  `api`, `worker` (plus one-shot `migrate`).
- Queue state is transactional with domain data — enqueue of the first job commits atomically
  with the news item; inspection/debugging is plain SQL.
- Retries, backoff, attempt counting, and dead-lettering are ordinary column updates — visible
  in the audit trail and logs.
- Polling adds up to ~200 ms of latency and some idle DB load; upgraded to `LISTEN/NOTIFY` in
  M3 (ADR-0006 covers the SSE side).
- No built-in fan-out, priorities, or per-queue rate limiting; `run_at` ordering (`ORDER BY
  run_at, created_at`) is the only scheduling policy in M1.
- Queue load shares the database with application traffic — acceptable at this scale.
